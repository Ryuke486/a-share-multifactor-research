# Stage 9 证据工作流继任设计

**状态：** 已批准并进入实现；现有 attempt 保持只读。

## 问题

`stage9-final-20260724-763d489` 已完成官方公告查询和文档下载，但复验发现：

- 20,623 个文档缓存中，20,621 个是可解析 PDF；
- 2 个所谓文档实际是 HTML 错误页；
- 复核队列有 20,627 行，但旧协议没有把人工审核结果发布为两类
  `ready` execution coverage 的合法入口；
- 旧代码把研究结果、最终执行规则和证据采集实现共同绑定到一个 Git
  身份，导致证据流程的局部缺陷扩大为 Stage 7/8 全量重跑。

降低事实正确性门槛不可接受。需要降低的是**失效范围**和**重复传输量**。

## 核心决定

1. 将协议身份拆成三个独立域。
2. Stage 8 必须演练从文档准入到两类覆盖原子发布的完整
   pre-resume 工作流。
3. 仅证据工作流身份变化、研究身份未变化时，Stage 7/8 研究结果可按哈希
   复用，只做 change-impact 审计和协议继任封印。
4. 新 attempt 可以从旧 attempt 导入已验证的原始查询和 PDF；只有缺失、
   无效或漂移的对象进入精确补采清单。
5. 新 attempt 可复用已经逐文件验证的不可变最终期日面板，但必须发布绑定
   旧 claim、面板 manifest、原始输入清单和 v4 协议身份的复用凭证。
6. 两类 execution coverage 必须作为一对验证并原子发布；任何一类失败时，
   外部都看不到半套 `ready` 输入。
7. 大规模人工审核按证券分成不可变小批次；中断只影响未完成批次，但最终发布
   仍必须重新满足全队列、全候选的精确核销。

## 三类身份与失效范围

| 身份域 | 主要内容 | 变化后的最小必做工作 |
|---|---|---|
| research result | Stage 7 验证结果、Stage 8 稳健性结果及其输入哈希 | Stage 7/8 研究重跑 |
| final execution | 冻结候选、交易规则、成本、组合、评价及执行契约 | 最终执行预演和重封 |
| evidence workflow | 查询、路由、PDF 准入、候选恢复、人工审核、覆盖发布和导入 | 完整证据工作流预演和重封 |

只有机器可读 change-impact 审计证明 research result 身份完全相同，才允许复用
既有 Stage 7/8 研究文件。代码改动本身不能作为“结果仍然一样”的证明。
protocol-only 路径还必须证明 `final_execution_rehearsal_required=false`，并且
`changed_domains` 精确等于 `["evidence_workflow"]`；否则发布、授权和日面板
复用均失败关闭。

## 工作流边界

### 1. 文档准入与隔离

- 下载成功不等于文档有效。
- 只有可由 PDF 解析器打开、非加密且至少一页的字节可以进入文档缓存。
- HTML、空响应、加密 PDF、不可读 PDF 和零页 PDF 进入不可覆盖的 quarantine。
- quarantine 默认不重试；只有显式精确补采才允许再次请求。
- 可转债“停止转股”和“转股价格调整”在公司行动通用关键词之前排除，避免
  再次误路由。

### 2. 公司行动候选

- BaoStock 只生产候选，不生产执行事实。
- 查询按证券和经营年度拆成不可变小包；中断后只查询缺失包。
- 每个响应都校验字段、行宽、证券范围、经营年度和日期语义。
- 完整快照必须精确核销全部证券年度查询。

### 3. 人工审核

- 每个公告队列行必须有且只有一个决定：
  `relevant`、`irrelevant` 或 `unusable`。
- 每个结构化候选必须有且只有一个 disposition：
  `accepted`、`corrected` 或 `rejected`。
- substantive 决定和执行事实只能引用已缓存且通过 PDF 准入的官方文档。
- 修正必须同时保留原字段、修正字段和修正理由。
- 审核提交不可变，并绑定队列、候选快照、审核者和带时区时间。
- 批次计划按证券划分队列和候选，同一证券不能跨批；计划绑定完整队列和候选
  manifest，任何输入漂移都会使整份计划失效。
- 每个批次槽只能发布一次不可变决定；相同字节可幂等恢复，冲突字节不得覆盖。
- 候选、执行事实与其引用的官方公告必须属于同一证券，跨证券 PDF 引用失败关闭。
- 缺少任一批次时不能汇总；全部批次齐备后仍调用原有全量审核门禁，批次不是
  对事实标准或精确覆盖标准的豁免。

### 4. 覆盖发布

- 公司行动和证券事件覆盖先在 staging 中共同物化和校验，再一次性公开。
- 零事件证券记录 `event_count=0`，不制造虚假 PDF 或 `evidence_id`。
- 查询包和 PDF 作为 attempt 级共享证据被引用，不在两类覆盖中重复复制。
- 每次加载都重验共享证据路径、大小和 SHA-256；漂移立即使覆盖失效。

### 5. 证据导入

- 目标必须是新授权、新 seal 和新 attempt；不能原地改写旧 attempt。
- 官方身份响应和查询包按原始字节导入，再以目标 attempt 身份重建索引。
- 旧文档逐份通过新 PDF 门禁后发布到目标缓存。
- 当前已知迁移结果应为 20,621 份可复用 PDF，2 个 URL 进入精确补采；
  正式数量仍以新 attempt 的导入报告为准。
- 复核队列和审核提交不能跨 attempt 直接复用，必须由目标 attempt 的目录、
  路由和候选快照重建并重新绑定。

### 6. 最终期日面板复用

- 既有日面板继续作为共享不可变数据集，不因证据工作流代码变化重建。
- 复用前重验旧 attempt、旧 seal、消费账本、数据 claim、面板 manifest、
  全部原始输入清单以及目标 v4 change-impact 决定。
- 目标 preparation 使用 schema v2，并把复用凭证的路径、大小和 SHA-256
  写入自身 manifest；后续 preparation 和信号入口重复验证同一凭证。
- 任一输入、面板或来源身份漂移都失败关闭，不能退化为静默重建或无凭证复用。

## Stage 7、8、9 的统一门禁

Stage 8 的 evidence-workflow readiness 必须包含六份可哈希报告：

1. PDF 准入和反例；
2. 候选采集中断恢复和精确覆盖；
3. 审核队列/候选字段级核销；
4. 两类覆盖原子发布、零事件和共享证据漂移；
5. 跨 attempt 证据导入及仅补采无效项；
6. 2017–2021、至少 100 只证券、最终测试期零读取的历史预演。

第 6 项由两部分组成：真实 100 只证券历史公告目录的全量重路由，以及人工
夹具上的文档、字段审核和双覆盖发布端到端反例。它不声称 408 份历史候选 PDF
已经逐份完成人工字段审核。

缺少任一报告，v4 协议不能封印，Stage 9 不能获得新授权。

## 当前 attempt 的边界

- 不覆盖、删除、归档或修补现有证据。
- 不在旧 Git/tree 绑定下执行新代码。
- 不执行 `resume`，不读取最终测试结果，不进入 Stage 10。
- 新实现完成、全量验证、历史预演、干净提交和 v4 关闭封印之后，才请求新的
  一次性授权。

## 验收

- 已知两类 HTML 错误页在准入层失败并被隔离；
- 中断的候选采集只补缺失查询；
- 队列和候选均精确核销；
- 两类 coverage 只能成对变为 `ready`；
- 零事件不依赖虚假文档；
- 旧有效查询和 PDF 可导入，新网络请求只面向精确缺失清单；
- 新 attempt 通过显式 v4 复用凭证使用既有最终期日面板，不重建 2022–2025
  日面板；
- research result 身份不变时，协议继任发布复制并重验既有 Stage 7/8
  研究产物，不重新计算研究结果；
- 所有正式发布仍要求干净 Git 身份、不可变 lineage 和关闭状态 opening
  ledger。
