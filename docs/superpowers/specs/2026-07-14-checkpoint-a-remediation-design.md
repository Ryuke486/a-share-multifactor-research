# 检查点A与阶段五审计修复设计

## 1. 目标

在不改变研究问题、样本划分、候选因子、因子方向、主复合方案和主目标组合的前提下，修复检查点A发现的血缘、统计口径、诊断、配置一致性与发布审计问题，使阶段五成为阶段六可复现、可追溯且接口稳定的正式输入。

本次允许修正复合相关性统计口径，由此产生的相关性报告数字变化属于方法纠错，不得用于更换因子、调整窗口、改变合成权重或选择更有利的组合。

## 2. 不变边界

- 2005–2016仍是唯一评价区间；2017–2025继续封存；
- candidate仍为阶段四冻结的6个因子；
- watch、reject与`log_market_cap`不进入正式收益合成；
- 主复合方案仍为`family_equal`；
- 主目标组合仍为`size_stratified_buffered`；
- 组合规模、规模分组、组内数量和缓冲排名不变；
- 不实现阶段六成交、税费、滑点、涨跌停、T+1、整手、订单或NAV；
- 不重写`AGENTS.md`的项目方向与阶段规划。

## 3. 总体方案

采用“阶段五局部修复 + 通用审计能力小幅下沉”，不进行全仓库重构。

```text
阶段四正式产物
  -> input gate
  -> composite scores
  -> target weights
  -> diagnostics
  -> publication gate
  -> 阶段五冻结产物
```

通用能力只覆盖阶段五、六、七都会使用的稳定概念：文件记录、数据集契约、阶段血缘和原子发布。因子合成、目标组合和统计评价仍保留在各自领域模块，不进入通用层。

### 3.1 审计发现与关闭矩阵

本设计保留检查点A原有A-01至A-08编号，并将设计审查新增的原子发布问题记为A-09。实现计划、测试和复查报告必须继续使用这些编号，不得只写笼统的“已修复”。

| ID | 原始问题 | 严重度 | 主要修复位置 | 最低关闭证据 |
|---|---|---|---|---|
| A-01 | 阶段五只校验部分阶段四文件，实际读取的日面板分区未全部绑定 | 阻断 | `audit/records.py`、输入门禁 | 替换任一实际输入后在计算前失败 |
| A-02 | 阶段五尚未形成可追溯冻结版本 | 阻断 | 代码身份、冻结流程 | 正式run来自用户授权后的干净提交，代码身份可复验 |
| A-03 | 组合诊断、排除原因和异常warning不完整 | 重要 | `portfolio/diagnostics.py` | 人工夹具可手算复核，异常月份产生结构化warning |
| A-04 | 复合相关性使用跨月份池化口径，不符合月度横截面等权设计 | 重要 | `combination_evaluation.py` | 不等月度样本量反例证明采用月度Spearman等权平均 |
| A-05 | 配置与核心逻辑存在重复硬编码，配置未完全驱动执行 | 重要 | 配置对象、合成和组合接口 | 修改合法配置后行为同步变化，非法方法被白名单拒绝 |
| A-06 | CLI暴露子阶段但运行时只允许`all`，与计划不一致 | 重要 | CLI、README、阶段五计划 | 公开CLI只暴露安全的完整发布命令，文档与行为一致 |
| A-07 | manifest元数据与核心数据集契约不足 | 阻断 | `audit/contracts.py`、`audit/lineage.py`、manifest | 每张核心表记录并通过schema、主键、日期、有限值和哈希契约 |
| A-08 | `combination_pipeline.py`同时承担计算、诊断、报告、血缘和发布 | 结构风险 | 编排层拆分 | 编排层不再定义哈希、契约、发布、报告或绘图实现，职责检查通过 |
| A-09 | processed与artifacts顺序替换存在崩溃窗口，不能称为原子发布 | 阻断 | `audit/publication.py` | 单一发布身份切换；失败或崩溃后读取方只能看到完整旧版或新版 |

每个编号在检查点A复查报告中必须给出：代码身份或修复提交、测试名称、真实数据证据、剩余限制和最终状态。A-01至A-07及A-09只有在对应反例测试及真实数据复查均通过后才能标记关闭；A-08的通过标准是职责边界满足上表，而不是追求机械性的文件行数。

## 4. 组件设计

### 4.1 通用审计基础层

新增小型`audit`包，职责限定为：

- `records.py`：生成并验证文件路径、字节数和SHA-256；
- `contracts.py`：描述并验证schema、主键、日期范围、行数与有限值规则；
- `lineage.py`：记录上游文件、配置哈希、代码身份和生产阶段；
- `publication.py`：管理不可变run目录、完整校验、单一`CURRENT`发布指针和失败清理。

这些对象必须与金融研究逻辑无关，不知道因子名称、组合规则或交易制度。

### 4.2 阶段五输入门禁

输入门禁消费阶段四`lineage.json`，验证：

- `factor_panel`、分类表、Rank IC、forward returns和相关矩阵；
- 日面板manifest、质量报告以及容量代理实际读取的年度分区；
- 文件大小和SHA-256与阶段四血缘一致；
- 阶段四核心表schema、主键和日期范围符合契约；
- candidate名称、因子族和`score_size_neutral`口径与冻结注册表逐项一致。

任何缺失、替换、越界或族映射错误在读取并计算阶段五结果前失败。

输入门禁还必须形成“实际消费文件集合”：

- 阶段五运行期间实际打开的每个上游文件必须出现在血缘记录中；
- 每条记录包含相对路径、文件角色、字节数和SHA-256；
- 血缘声明但本次未消费的文件必须标记用途，不能假装参与了计算；
- 新增任何读取路径但未同步加入输入门禁时，测试必须失败；
- 绝对路径只作本机诊断，不参与研究身份哈希。

### 4.3 配置驱动的一致性

组合与组合校验函数显式接收：

- 分析起止日期；
- 方法列表和主方法；
- 最低有效因子族数；
- 滚动IC窗口、最低月份和收缩比例；
- 组合规模、规模组、组内数量和缓冲排名。

冻结注册表仍作为白名单，配置不能增加未批准的方法或因子。核心逻辑不得重复硬编码与配置相同的日期和阈值。

### 4.4 相关性统计纠错

复合方案之间、复合方案与单因子之间统一采用：

1. 每个信号月在共同证券截面计算Spearman相关；
2. 无法计算的月份记录原因；
3. 对有效月份等权平均；
4. 汇总输出`mean_correlation`、`common_months`、`invalid_months`和主要异常原因；
5. 同时输出逐月相关性明细，不用一个汇总`reason`代替月度证据。

不同月份证券数量不得改变月份权重。新增不等样本量反例，证明池化相关与月度平均不同时选择后者。

逐月明细固定主键为`(date, left_name, right_name)`，至少包含：

- `common_count`；
- `correlation`；
- `valid`；
- `reason`。

共同证券少于3只、任一序列为常数或相关系数非有限时，该月标记无效并记录原因，不进入均值。因子对名称按字典序规范化，禁止同时保存A-B和B-A。

### 4.5 目标组合诊断

在现有换手、持仓数、最大权重、HHI和有效持仓数上增加：

- `top100_equal`与主组合的月度持仓重合率；
- 两组合单边目标换手及差值；
- 五个规模组的目标数和实际数；
- 组合加权规模、6个候选因子和3个因子族暴露；
- 使用信号日及以前20日成交额的容量代理；
- 覆盖下降、异常换手、规模组不足和成交额历史不足warning。

`top100_equal`未入选股票不生成逐证券全量日志，以避免产生无研究价值的大文件。只保存聚合排除原因计数；如果计划原文要求逐证券原因，则将计划修正为该精简口径并记录原因。

### 4.6 CLI和发布

公开CLI只保留`all`完整发布路径。内部函数仍可单独测试，但不承诺用户可从任意半成品阶段续跑。

完整运行顺序：输入验证、计算、写入新的不可变run目录、数据集契约验证、manifest生成、报告生成、重新读取校验，最后只切换一次`CURRENT`发布指针。任何失败均保留上一版正式产物。

发布布局固定为：

```text
processed/factor_combination/
  CURRENT.json
  releases/
    <run_id>/
      datasets/
      artifacts/
      manifest.json
      lineage.json
```

- `<run_id>`在单次发布中唯一，run目录写完后不可原地修改；
- `CURRENT.json`只包含run ID和manifest哈希，通过同文件系统内`os.replace`单次切换；
- 本轮只实现通用发布解析器及阶段六兼容性测试，不实现阶段六交易模块；未来阶段六必须通过该解析器读取`CURRENT`对应的`datasets`，不得扫描“最新目录”；
- `artifacts/factor_combination/`如继续保留，只作为面向用户的便利镜像，不是阶段六的权威输入；
- 崩溃发生在指针切换前时仍读取旧run；切换后只读取已完整校验的新run；
- 启动时识别没有被`CURRENT`引用的未完成run，隔离或清理，但不得删除当前run；
- 不再使用“双目录原子替换”表述，也不依赖进程内异常处理模拟跨目录事务。

阶段五manifest为每个核心对象记录：

- 相对路径、字节数、SHA-256；
- schema、主键、行数；
- 最小和最大日期；
- 生产模块和阶段；
- 配置哈希与上游血缘身份。

manifest自身使用确定性JSON序列化；列表顺序、schema字段顺序和浮点表示必须稳定。`CURRENT.json`记录manifest哈希，使数据集、报告和发布身份绑定为同一个run。

### 4.7 模块收敛

从`combination_pipeline.py`移出：

- 血缘与manifest构建；
- 输出契约验证与发布；
- 报告文本和图表写出。

编排层只负责调用顺序和数据对象传递。此次不重构阶段四，也不为了统一风格修改无关模块。

编排层可以保留阶段顺序、依赖注入和顶层异常传播，但不得继续定义文件哈希、数据集契约、发布替换、报告正文或绘图实现。A-08以职责边界和独立测试判断，不设置容易诱发机械拆文件的硬性行数上限。

### 4.8 代码身份

正式研究期运行必须产生唯一代码身份。优先方案是要求工作树干净，并记录完整Git commit。若因审计修复尚未提交而确需运行，则必须同时记录：

- 基础Git commit；
- `dirty=true`；
- 规范化Git diff的SHA-256；
- 实际参与阶段五运行的源码文件路径、字节数和SHA-256；
- Python版本和关键依赖版本。

仅记录Git commit但忽略未提交修改不构成有效代码身份。发布前的最终正式运行应使用干净、已提交的工作树；dirty身份只允许用于修复验证，不得作为阶段六冻结输入。由于项目禁止未经用户请求提交，完成修复和验证后必须先取得用户明确授权，再提交并生成正式冻结run。

## 5. `AGENTS.md`与项目文档

`AGENTS.md`无需改变以下内容：项目定位、研究优先级、样本划分、防泄漏规则、阶段路线和模块边界。

修复完成后只更新事实性状态：

- 阶段五实际运行结果与限制；
- 检查点A复查状态；
- 主复合方案和主目标组合已经冻结；
- 2017年以后仍未读取；
- 阶段六仍需用户明确批准。

通用审计增强主要体现在源码`audit`包、阶段五manifest/lineage和检查点A复查报告，不在`AGENTS.md`中扩展大段实现细节。

## 6. 测试策略

按测试驱动顺序实施：

1. 日面板分区、manifest或上游文件被替换时输入门禁失败；
2. candidate因子族或score口径被修改时失败；
3. 日期、最低族数和方法列表确实驱动执行；
4. 当期和未来IC不能改变历史权重；
5. 月度截面相关采用月份等权而非全样本池化；
6. 两组合重合率、换手差和异常warning可手算；
7. manifest包含契约元数据且篡改输出可被发现；
8. 发布失败或在`CURRENT`切换前中断时保留上一版完整产物；
9. 切换后阶段六解析器只能读取同一run的datasets、artifacts和manifest；
10. dirty工作树只记录commit时身份校验失败，补齐diff与源码哈希后可用于修复验证；
11. 阶段一至五全量回归与ruff通过。

真实数据验证先使用人工夹具，再在相同代码身份、配置和上游输入下运行2005–2016完整研究期两次。

双次复现比较规则：

- 必须逐文件哈希一致：Parquet、CSV、研究结果JSON和配置快照；
- 语义内容必须一致但允许字段不同：lineage和manifest中的`run_id`、运行时间及临时路径；
- 比较前所有表使用固定主键稳定排序，JSON使用确定性序列化；
- PNG只检查文件存在、尺寸、生成输入哈希和绘图配置，不作为核心逐字节确定性门禁；
- 两次运行必须生成独立run，比较完成前不得用第二次结果覆盖第一次证据；
- 任何研究数值差异都视为复现失败，不能归因于“浮点波动”而直接放行。

## 7. 完成与冻结标准

- 审计报告A-01至A-07及A-09按关闭矩阵逐项关闭；
- A-08达到明确的编排职责边界；
- 阶段五核心表无重复键、越界、非有限值或权重不守恒；
- 上游任何实际输入变化都会在计算前失败；
- 相关性数字可以变化，但研究决策和冻结参数不变；
- 全量pytest与ruff通过；
- 真实研究期结果连续两次可复现；
- 正式冻结run来自干净提交，并记录唯一代码身份、配置哈希、上游身份和输出manifest；
- 形成检查点A复查报告；
- 用户明确批准后才进入阶段六。
