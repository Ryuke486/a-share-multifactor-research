## 3. 必须修复：不修复不得进入阶段七

### B-01：公司行动发生时没有重建跨日pending订单

**严重度：** 阻断  
**影响范围：** 订单股数、成交金额、费用、换手、目标偏离、持仓和NAV。

#### 问题证据

当前执行顺序会在除权日调整持仓股数：

- `src/ashare_multifactor/execution/broker.py:126-164`

但后续仍直接执行原pending订单：

- `src/ashare_multifactor/execution/broker.py:318-557`

原订单数量是在除权前价格和持仓状态下计算的。送转或除息后，价格、持仓股数和目标股数尺度已经改变，继续使用旧的剩余股数会造成实际目标偏离。

人工反例：10送10期间，除权前目标订单为10,000股，首日成交100股，剩余9,900股。除权日持仓变为200股，但pending仍只买9,900股，最终持有10,100股；以除权后5元价格计算，组合只投入约一半目标资产。

正式release中：

- 共有3,920条非零送转事件；
- 168笔真实订单跨越送转生效日；
- 因此当前正式结果已受到潜在影响，不是纯理论边界情况。

#### 推荐修复

不要简单用 `(1 + share_ratio)` 乘pending剩余股数。未成交买单没有在股权登记日持股，不享有送转权益，机械倍增在复杂事件、部分成交和现金分红情况下仍可能错误。

推荐采用“公司行动触发目标重建”：

1. 在执行器中显式保存当前仍生效的冻结目标权重 `active_target_weights`；
2. 除权日先处理应收股利、送转股和证券转换；
3. 若当天同时存在新月度信号，按既有 `new_signal` 规则撤销旧pending，并直接用新目标重建；
4. 若没有新信号，则只撤销受公司行动影响证券的pending订单；
5. 事件原因记录为 `corporate_action_rebase`；
6. 使用公司行动处理后的持仓、开盘前NAV和当日原始开盘价，根据当前冻结目标权重重新计算目标股数；
7. 新订单继续遵守100股、T+1、现金、容量、涨跌停和稳定排序规则；
8. 不使用当日收盘、高低价或未来成交额重建订单。

该方案保持“目标权重在两次月度信号之间不变”，只修正公司行动导致的股数尺度变化，不构成策略调参或每日主动再平衡。

#### 必需测试

- [ ] pending买单跨10送10事件，除权日按原目标权重重建；
- [ ] pending卖单跨送转事件，卖出缺口按调整后持仓重建；
- [ ] 部分成交订单跨公司行动，旧订单先取消且成交历史不被改写；
- [ ] 现金分红除权日同时存在pending订单时，用含应收股利的开盘前资产重建；
- [ ] 同一天既有公司行动又有新信号，只执行一次重建，以新信号优先；
- [ ] 多个同日公司行动不会重复重建或重复应用；
- [ ] 重建后的买单仍为100股整数倍，卖单不超过可卖股数；
- [ ] 修改未来收盘、高低价或当日总成交额不改变开盘重建结果；
- [ ] 原人工反例修复前失败、修复后通过。

#### 关闭标准

## 4. 推荐优化：不阻断阶段七，但建议优先处理

### O-01：消除准备度报告冲突

**当前问题：**

- `artifacts/formal_backtest/readiness_report.md`仍显示 `conditionally_ready`；
- 当前正式release内部报告显示 `ready`。

根目录文件属于旧诊断阶段，但文件名和位置容易让用户或后续代理误认为它仍是权威状态。

**推荐改法：**

- 权威状态只允许通过 `processed/formal_backtest/CURRENT.json` 解析；
- 根目录便利报告改名为 `latest_audit_snapshot.md` 并写明非权威，或删除便利镜像；
- README明确说明不得直接读取根目录旧报告判断当前状态；
- 增加测试：发布新run后，文档引用必须指向release解析器或同步的权威快照。

**优先级：** 高。它不改变计算，但直接影响可审计性和答辩可信度。

### O-02：拆分788行撮合器

**当前问题：** `execution/broker.py`同时负责公司行动、订单生成、成交、三场景账本、估值和输出组装，共788行，已超过项目的小文件、低耦合要求。

**推荐边界：**

```text
execution/
  broker.py                 # 仅保留逐日编排
  corporate_action_engine.py# 应收、送转和证券事件
  order_rebalancer.py       # active target、撤单与订单重建
  matcher.py                # 可交易性、容量、价格和成交
  scenario_runner.py        # 三场景独立运行与汇总
```

拆分应保持现有公开接口 `run_backtest()` 不变，先用现有580项测试保护行为，再移动职责；不要同时修改金融规则。

**优先级：** 中高。建议与B-01一起做有限拆分，因为pending重建天然属于独立 `order_rebalancer`；不建议借机重构全部execution包。

### O-03：收敛477行正式管道

**当前问题：** `formal_backtest_pipeline.py`同时负责准备度、运行、输出、报告、lineage和双次比较。

**推荐边界：**

```text
research/
  formal_backtest_pipeline.py   # 顶层顺序和门禁
  formal_backtest_readiness.py  # 数据准备度与来源覆盖
  formal_backtest_outputs.py    # 数据集、报告和artifact写出
```

本项可在阶段七开始前或阶段七首次需要复用发布接口时处理。若暂不拆分，阶段七不得继续向该文件堆叠验证期和稳健性逻辑。

**优先级：** 中。

### O-04：移除单次运行内部的冗余场景账本

当前 `run_backtest()`已经独立运行完整成本、仅显性费用和零成本三次，但 `_run_backtest_once()`内部又维护三个ledger。真实release目前三者数值可以对齐，但双层场景结构增加理解和公司行动同步风险。

**推荐改法：**

- `_run_backtest_once()`只维护一个ledger并返回单场景结果；
- `run_backtest()`负责运行三次并为每张表增加 `scenario`；
- `scenario_reconciliation`直接拼接三个独立run各自的 `reconciliation`；
- 删除单次运行中的 `explicit_cost_nav` 和 `zero_cost_nav` 临时列；
- 保留三场景独立成交和现金约束，不改成同一成交路径的事后扣费。

**优先级：** 中。它能明显降低B-01修复时的状态同步复杂度。

当前阶段六计划被收敛为简短完成清单，便于阅读，但原详细任务、数据门禁和验收口径不再直接可见。

**优先级：** 中低。
